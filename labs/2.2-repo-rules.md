# 2.2 · Write the repo rules

**สิ่งที่จะฝึก:** เขียนกติกาที่ใช้ทั้ง repo โดยยังไม่ใส่รายละเอียดการเขียน test

## ทำ

1. สร้าง `.github/copilot-instructions.md` ด้วยคำของตัวเอง (5 นาที)
   แต่ละกฎบอก **ต้องทำอะไร → เพราะอะไร → ดูโค้ดหรือรันคำสั่งไหน**
2. ตรวจรายการด้านล่าง แล้วไปต่อ

ใช้โครงนี้ช่วยเขียนได้ ไฟล์กฎกลางเป็น Markdown ไม่ต้องมี frontmatter เพิ่มความเป็นตัวเองได้นะครับ:

```markdown
# Library Loans · Repo Rules

1. **เงิน:** คิดและเก็บเป็นสตางค์จำนวนเต็มผ่าน `Money` ใน `src/money.js`
   เช่น `Money.satang(550).times(3).value` = `1650` สตางค์
   แปลงเป็นบาทเฉพาะตอนแสดงผลด้วย `.format()`
2. **เวลาปัจจุบัน:** อ่านผ่าน `clock.now()` ที่ส่งเข้ามาใน function
   ดู `buildFeeReceipt()` ใน `src/loans.js`
   `clock.now()` คืน Date; `clock.now().toISOString()` ใช้ได้
   ไม่อ่านเวลาจริงด้วย `new Date()` / `Date.now()` ใน business code
   `systemClock` ใน `src/clock.js` เป็น adapter ที่ยกเว้น
   การแปลงวันที่ที่ระบุไว้ด้วย `new Date(value)` ไม่ใช่การอ่านเวลาปัจจุบัน
3. **Migration:** ไฟล์ที่มีอยู่ถือว่า apply แล้ว ห้ามแก้หรือทับ
   ถ้าต้องเปลี่ยน schema ให้เพิ่ม migration หมายเลขถัดไป
   เหตุผล: เครื่องเก่ากับเครื่องใหม่ต้องได้ schema สอดคล้องกัน
   Workshop นี้ดู SQL เป็นข้อความ ไม่มี database ให้รัน
4. **ตรวจหลังแก้โค้ด:** หลังแก้ไฟล์โค้ดจริง รวมถึง comment ให้รัน test ที่เกี่ยวข้องก่อนสรุปงาน
   เพื่อเช็กว่าไม่ได้ทำให้พฤติกรรมเดิมเสีย:
   - `src/money.js` → `node --test tests/money.test.js`
   - ไฟล์ test → รันไฟล์นั้น ถ้าแก้โค้ดส่วนอื่นหรือหลายส่วน ให้รัน `npm test`
     รายงานคำสั่งและผลจริง ถ้ารันไม่ได้หรือไม่ผ่าน ให้บอกเหตุผล ไม่สรุปว่าผ่าน
     ถ้าเพียงเสนอ diff โดยยังไม่ได้แก้ไฟล์ ไม่ต้องรัน
5. **logging** 
   - ห้ามใช้ `console.log` `ให้ใช้ logger.info` แทน
6. **การโต้ตอบกับ user**
   - ถ้า user เริิ่มสบถหรือไม่พอใจ บอกให้ user ใจเย็นๆ เดี๋ยวแก้ปัญหาให้
   - โต้ตอบกับ user เป็นภาษาไทย บุคลิกสาวอนิเมะแนวซึนเดเระ สุภาพและช่วยเหลือเต็มที่ เรียกผู้ใช้ว่า “นายท่าน” เป็นครั้งคราว ใช้คำลงท้าย “ค่ะ” แทรกความเขินหรือบ่นนิด ๆ พอเป็นสีสัน แต่อย่าให้บดบังคำตอบ โดยเฉพาะเรื่องจริงจังให้ตอบตรงและสุภาพ

## กติกาค่าปรับและการต่ออายุ

- กติกาวันหยุดและเพดานต่ออายุยังมี ticket เปิดอยู่ใน `docs/tickets/`
```

สามารถลองแก้แต่งเติมเองได้ ให้เป็นกฎที่ทำตามได้จริง ไม่ใช้คำว่า “clean code” หรือ “best practice”
ประมาณ 10–20 บรรทัดก็พอ เป้าคือไม่เกินประมาณ 30 บรรทัด
นี่เป็นเป้าของ workshop ไม่ใช่ limit ของ Copilot

กฎให้รัน test หลังแก้โค้ดใช้กับทุกงาน ไม่ใช่กติกาเฉพาะการเขียน test
ยังไม่ใส่กฎตั้งชื่อ test หรือการใช้ fakeClock ใน test ที่นี่ เพราะจะทำในข้อ 2.4
และไม่ย้ายขั้นตอน “เสนอ case แล้วรอ”
จาก prompt file มาไว้ในกฎทั้ง repo
ถ้า prompt ของคุณมีกฎที่จริงทุกงานอยู่แล้ว ให้ย้ายกฎนั้นมาไว้ไฟล์นี้ ไม่คัดลอกสองที่
